## 学习单元 2.1：隔离业务规则与存储通信细节

- 所属实现任务：任务 2，背包业务规则 Service
- 痛点提出者：AI 根据现有实现提炼
- 问题场景：生产环境中，服务器持久化数据应是玩家背包的唯一可信来源。当前内存实现只用于本地 Demo 和自动测试；Unity 客户端未来应通过服务器 API 获取数据，而不是在运行时从多份权威数据中任选一份。
- 当前做法的后果：如果移动、交换、合并和拆分规则直接包含 SQL、网络请求或内存容器操作，规则就会和存储、通信及测试环境绑在一起。
- 约束：服务器数据保持唯一可信；业务规则不因 SQL 或网络细节而改变；没有 MySQL 时仍能测试规则；本单元先讨论职责和调用关系，不查看现有答案代码。
- 用户初步方案：玩家背包的真实数据应该只有一个来源，即服务器；内存数据只是当前阶段的临时方案，因此不应把它们理解成多份可随意切换的真实数据源。
- AI 评审：用户正确地区分了两个职责，并进一步提出由规则部分生成一组状态变化，再由保存部分统一提交。这个通用变化方案能够同时表达拆分和合并，比只保存“格子移动”更完整。用户随后又推导出多条变化必须由一个外层操作协调，任何一条失败都应撤销全部变化；这个机制在数据库中称为事务。事务不是额外传入一个“同时执行”布尔参数，而是保存部分开始事务、执行同一组创建/更新/删除，全部成功后提交，任一失败则回滚。文件数量不是关键，职责边界和一致性才是关键。“按物品类型判断操作”的细节留到学习单元 2.3 讨论。
- 用户修正方案：规则部分把一次操作转换成多条状态变化，保存部分提供一个通用的“保存变化”入口。拆分 10 个苹果中的 3 个时，一条变化把原格数量更新为 7，另一条变化创建目标格的 3 个苹果；外层保存操作协调全部变化，任一失败时让整组变化失败并恢复原状。
- 最终选择及原因：规则部分生成包含创建、更新、删除的变化集合；保存部分通过一个通用入口原子地保存整组变化。MySQL 实现使用事务保证全部提交或全部回滚。这样业务规则不包含 SQL 或网络细节，多条变化也不会只保存一半。
- 对应代码：
  - `InventoryChangeType.cs`：定义创建、更新、删除三种变化。
  - `InventoryChange.cs`：表达一条待保存的物品状态变化。
  - `InventorySaveResult.cs`：返回创建操作生成的新物品实例。
  - `IInventoryRepository.cs`：只保留加载和通用 `SaveChangesAsync`。
  - `InMemoryInventoryRepository.cs`：先在数据副本中应用整组变化，全部成功后整体替换正式数据；任一失败时不提交副本。
  - `InventoryService.cs`：移动、交换、合并、拆分、使用和丢弃都先生成变化集合，再统一保存。
- 验证结果：临时 .NET 控制台项目编译为 0 警告、0 错误；合并、拆分、交换、部分丢弃、使用、搜索和重新加载通过；人为让变化集合的第二条删除失败后，第一条数量更新未进入正式数据，回滚行为通过。
