# 需求澄清文档

## 用户原始需求

在当前 Unity 项目中构建一个 MVC 背包系统。玩家打开背包后，可以查看、移动、搜索、使用和丢弃物品；背包数据需要接入本地 MySQL，通过增删改查支持大量玩家物品实例。

## AI 澄清评审

### 已明确部分

- 项目形态：Unity 中可运行的完整 Demo。
- 架构目标：采用 MVC 思路，但具体职责和脚本由后续施工流程逐步形成。
- 数据目标：本地启动 MySQL，Demo 与数据库交互。
- 数据区分：物品定义数据与玩家拥有的物品实例数据分开。
- 核心交互：移动到空格、交换、堆叠合并、拆分、搜索、使用、拖出丢弃。
- 使用效果：至少接入可验证的具体效果，不只扣减数量。

### 歧义与缺口

- 背包容量、默认格子数和示例物品列表尚未最终确认。
- 图标资源来源和第一版视觉表现尚未确认。
- 装备随机词条、强化、耐久等实例属性只确认需要保留扩展可能，第一版范围尚未细化。
- 流程 4.1 已选择 `MySqlConnector 2.5.0`；连接字符串保存在当前 Windows 用户环境变量 `LEARN_INVENTORY_DB_CONNECTION`，不写入源码或场景。后续写入流程仍需逐步确认数据库权限和事务边界。

### 边界与风险

- Unity 直连 MySQL 只用于本地学习 Demo；生产环境应由服务器作为可信入口。
- 大规模物品数据需要服务器持久化，但客户端只加载当前玩家当前需要的数据。
- 背包操作不仅是 CRUD，还包含交互规则、失败反馈和多数据变化的一致性；这些问题应在对应流程完成后根据实际代码审查。

## 用户补充与修正

- 明确要求支持交换、堆叠合并、拆分、拖出丢弃和使用。
- 希望物品使用接入具体效果系统。
- 希望最终得到包含 UI、交互、数据读写和效果反馈的完整 Demo。
- 希望先由用户提出整体施工路线，AI 检查是否覆盖需求；每完成一条流程后，AI 再主动提出真实痛点供用户解决。

## 最终确认需求

1. 玩家能够打开和关闭背包，并看到格子、物品、数量及必要反馈。
2. 物品能够移动到空格，也能与目标物品交换。
3. 同种可堆叠物品能够合并，并受最大堆叠数限制。
4. 可堆叠物品能够拆分到空格。
5. 玩家能够按名称、类型或标签搜索物品，搜索不改变真实背包数据。
6. 玩家能够使用物品，并看到至少一种具体效果及对应数量变化。
7. 玩家拖出物品后经过确认可以丢弃全部或部分数量。
8. 背包数据能够从本地 MySQL 加载，并在操作后正确保存。
9. 数据库连接、保存或非法操作失败时，Demo 不崩溃，并给出可见反馈或日志。
10. 物品定义与玩家物品实例明确分开，Demo 使用固定玩家 ID，同时保留多玩家数据表达。

## 明确不做的内容

- 完整联机同步、账号鉴权和反作弊服务端。
- 交易、商城、邮件、仓库和完整装备栏。
- 大规模性能压测和生产级分库分表实现。
- 完整美术、复杂动画和正式产品级视觉设计。

## 暂定假设

- 第一版使用项目已有的 uGUI 和 Input System 能力。
- Demo 使用固定玩家 ID 和少量示例物品。
- 背包容量、示例数据和视觉资源可以在对应施工步骤中确认，不阻塞整体施工路线设计。
